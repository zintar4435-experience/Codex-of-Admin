Your own panel on your own server

Setting up Codex of Admin

From a clean server to the first working connection. No prior knowledge needed — everything step by step.

What you get in the end

A working server with the panel and a connection that doesn’t stand out. There are several schemes — from the fastest to the least noticeable — and they can be combined on one server. Which one to take is covered in step 06; if you don’t want to choose, there is a ready answer there too.

The panel interface is in Russian. Button and menu names are given here exactly as they appear on screen, in Russian, with an English translation in brackets — for example «Добавить» (Add).

00

What you need beforehand

  • A server — Ubuntu 22.04 or 24.04, x86_64, SSH access as root. A clean one: the panel installs everything it needs and takes ports 80 and 443.
  • A domain — your own, any. Free dynamic domains won’t do: they get blocked as whole zones, we’ve been through that.
  • A name for the panel — required. For example, the subdomain panel.example.com.
  • A name for the connection — not everyone needs one. The Reality scheme needs no domain at all; the “behind a real website” and NaiveProxy schemes require one, each its own. They are all just subdomains of one domain pointing to the same server.

The panel and the connection must use different names. The panel checks this and won’t let you save otherwise. The reason is simple: if they share a host, anyone who found your VPN has found your admin login too.

01

Domains and DNS

This step has one goal: make your domain’s names point to your server. It is done not on the server but in your registrar’s account — where you bought the domain. It takes five minutes, and you won’t need to come back to it.

Recommended — two records, and DNS is done for good

This is how our own server is set up.

  1. In the registrar’s account open the domain’s DNS settings and click “Add record”.
  2. Type — A. In the name field enter a single asterisk: *. In the value field — your server’s IP. Save.
  3. Add a second identical record, but with @ in the name field (some registrars leave the field empty instead of @). Save.

What you just did:

  • The asterisk means “any subdomain”. Now panel.example.com, the NaiveProxy name and any name you may need later already point to the server — whatever schemes you enable later, you won’t need to touch DNS again.
  • The @ record is the domain itself, example.com without a subdomain. The asterisk doesn’t cover it — and you need it if you take the “behind a real website” scheme on the bare domain.

For the careful — individual records

The only downside of the asterisk: your server also answers any random subdomain someone types. If you don’t like that, create separate records instead — all of type A and all with the value “server IP”:

Record nameWhat forWhen needed
panellogging in to the control panelalways
@ (and www, if you want an address with www)your website and the connection “behind” itonly scheme B (section 06·B)
a name for NaiveProxy — make one up, any word: files, cloud, anythingthe address NaiveProxy connects toonly if you use it (section 06·D)

The Reality (06·A) scheme needs no name at all — its absence from this table is not a mistake.

What it looks like at the registrar

The record form is called differently everywhere, but the fields are always the same. The most common confusion is the name field:

Field in the domain panelWhat to enter
“Name” / “Host” / “Subdomain” — all the same fieldonly the subdomain label: panel (without .example.com — the registrar adds it)
the same field, if the record is for the domain itself@ (some use an empty field)
the same field for an “any subdomain” recorda single asterisk: *
“Type”A
“Value” / “Address” / “Points to”your server’s IPv4
“TTL”leave it, any default works

If your registrar creates subdomains in a separate section (“Create subdomain”), it is the same A record from a different entrance: create the subdomain panel and give it the server’s IP. You never need to buy or register a subdomain separately — it “appears” when the record is created.

Cloudflare: turn off proxying for the record — the cloud must be grey (“DNS only”), not orange. The orange cloud sends traffic through Cloudflare’s servers, and the connections (Reality, NaiveProxy) won’t work.

AAAA records (IPv6): if the server has no IPv6, don’t create them. A leftover AAAA record from an old host pointing to someone else’s address breaks certificate issuance: Let’s Encrypt tries IPv6 first and hits a server that isn’t yours.

Records don’t spread across the internet instantly — usually minutes, sometimes up to an hour. Until the domain answers with your IP, the certificate won’t be issued. To check: ping panel.example.com (or nslookup panel.example.com) should show the server’s IP.

02

Installation

Log in to the server over SSH as root and run one command:

on the servercurl -fsSL https://raw.githubusercontent.com/zintar4435-experience/Codex-of-Admin/main/bootstrap.sh | sudo bash

It installs everything by itself: Xray, Caddy with NaiveProxy support, the panel itself, the services and the firewall. It takes a few minutes.

You will run the same command to update — it detects that the panel is already installed and updates only the code. The database and settings are not touched.

03

First login and HTTPS

  1. The installer showed the admin login and password at the end of installation — in the “ВОЙТИ В ПАНЕЛЬ” (Log in to the panel) box. Save them: the password is shown once. If you lost it, set a new one on the server: 
    on the server/opt/proxy-panel/venv/bin/python /opt/proxy-panel/run.py --create-admin --username admin --password 'NEW_PASSWORD'
  2. Open http://SERVER-IP:5000 and log in with those credentials.
  3. In the panel settings enter the panel domain — panel.example.com.
  4. Save. The panel gets a certificate and moves to https://panel.example.com by itself.
  5. Make sure it opens at the new address, and only then go further.

Port 5000 is the emergency entrance that bypasses the domain. Close it (section 04) only after the panel opens at https://panel.example.com — if something goes wrong with the domain, it will be your only way back in.

04

Security — right away, not later

Three things worth doing the same day, not “some day”.

  1. Turn on two-factor authentication in the panel settings. This is the main protection: passwords get guessed, the second factor doesn’t.
  2. Close port 5000. After the move to HTTPS it is no longer needed, and while it’s open it is a way into the admin panel that bypasses the domain: 
    on the serversudo ufw delete allow 5000/tcp
  3. If your host has its own firewall, leave only 22, 80 and 443 open.
05

Cover website

This is what it’s all about. Your domain must open a real website — otherwise the scheme doesn’t work.

The site files live in /var/www/decoy. Installation doesn’t create this folder — create it yourself and put a site there.

A ready-made site in one command

The simplest is to take our ready-made cover site — the same one that runs on the reference server:

on the serversudo mkdir -p /var/www/decoy
sudo git clone https://github.com/zintar4435-experience/Codex_site.git /var/www/decoy

Open your domain in a browser — an ordinary website should appear. That’s it, the cover is ready.

Your own site

If you want your own, create the folder and put the files in it (an index.html in the root is required):

on the serversudo mkdir -p /var/www/decoy

Any ready HTML template will do (a business card, a landing page, a portfolio). The point is that a person who opens the domain sees a website and isn’t surprised.

An empty folder is only half the job. A domain with a certificate but no site looks more suspicious than a domain without a certificate: “there is a site but no content” is exactly the anomaly automated checks look for. An empty folder is better than nothing, but a real site is better than an empty folder.

06

Which scheme to choose

The panel supports several methods, and they are not mutually exclusive — one server can run two at once. First, how they differ.

SchemeNeeds a domainSpeedStealthWhen to use
VLESS + Realitynomaximumhighby default
Behind a real websiteyesslightly lowermaximumwhere Reality gets cut
NaiveProxyyes, its ownmediumhighas a backup route
SSHnolowmediumwhen nothing else works

If you don’t want to choose, take the “VLESS + Reality” template as is (option A): it disguises itself as a large well-known site and leaves port 443 alone — the panel, NaiveProxy and your site work alongside. Option C (everything on one 443 under your domain) is less visible to scanners, but with some Russian providers such connections “freeze”: text gets through, pictures and pages don’t.

The panel also shows Trojan and Shadowsocks. Our app doesn’t understand them — it supports VLESS, NaiveProxy and SSH. Create them only if your people use third-party clients.

06·A

Option A — VLESS + Reality

The fastest and simplest: no domain for the tunnel, no certificate, everything comes up in one action.

How it works: the server imitates someone else’s TLS handshake — for example, presents itself as www.samsung.com. Anyone who doesn’t know the key really does land on the real site you disguise as.

In the panel: «Инбаунды» (Inbounds) → create → template «VLESS + Reality». The template fills in everything: in the «Маскировка» (Disguise) block «Под известный сайт» (As a well-known site) and the site www.samsung.com are already selected — no need to change them.

FieldValueWhy
EngineXrayReality exists only here
ProtocolVLESSReality doesn’t work with the others at all
TransportTCPrequired, the panel checks it
Portfilled in automatically (2083, 2087…)443 stays with the panel and your site. If the hint under the “Port” field says it’s closed, run the command shown there once on the server
Disguise«Под известный сайт» (As a well-known site)with some Russian providers, connections to little-known domains “freeze”; with a large site they don’t
Reality keysfilled in automaticallythe panel generates them, nothing to type
Flowxtls-rprx-visionthis is what gives the speed, see below

Don’t pick gRPC or WebSocket “for reliability”. Reality requires TCP specifically — on another transport the panel refuses. And even where such a combination can be built, it is slow: a second layer with its own flow control appears on top of the encryption, and on a long route that means slow connects and low speed. We investigated exactly such a case on a friend’s server — the complaints were exactly about this.

Reality’s weak spot is the mismatch. The connection goes to your IP but presents someone else’s name. Some filtering systems compare the two. Option C below removes the mismatch completely.

Another site to disguise as — click «Подобрать» (Pick) next to the “Site” field: the panel checks large sites and subnet neighbours from your server and lists suitable ones; one click and the site is filled in. Large sites are at the top — take those. You can also type your own and click «Проверить» (Check). The «Заметность» (Visibility) page has a «Проверить заметность» (Check visibility) button: it shows what a scanner coming to your server from outside sees.

06·B

Option B — behind a real website

There is no disguise as someone else’s site here: you have your own domain with your own site on it, and the VPN lives inside it on a secret path. From outside it is an ordinary HTTPS website — because it is an ordinary HTTPS website.

DNS for this scheme: the domain itself (the @ record from step 01) must point to the server. If you made the two records the recommended way, it’s already done.

In the panel: «Инбаунды» (Inbounds) → create.

FieldValueWhy
EngineXrayonly it has the mode checkbox
ProtocolVLESSthe only one the client supports
Transportws or httpupgradeCaddy proxies only an HTTP upgrade by path
Domainwww.example.comnot the panel’s — the panel checks this
Path/a7f3c1b9e28+ characters, not obvious
Behind a real websiteonthis is the mode itself

The path is a key, not decoration. /ws, /vpn, /api are found by brute force in minutes, and then the disguise stops working: from outside it’s visible that there is something behind the site. The panel rejects anything shorter than 8 characters. Take a random mix of letters and digits — and write it down; recovering it from the panel later is harder than it seems.

Reality can’t be turned on in this inbound, and the panel won’t let you. These are two different ways of handling encryption, and there is only one layer: here Caddy takes it on with your domain’s certificate, while Reality means there is no certificate at all and Xray imitates the handshake. The restriction applies to a single inbound only — on a server both schemes get along fine, see option C.

06·C

Option C — both schemes on one server

Recommended. The panel supports this specifically, and it is set up like this: just create both inbounds — from option A and from option B. Nothing else is needed.

What happens by itself:

  • Caddy moves to 127.0.0.1:8443 — inside the server, no longer facing outward.
  • Reality takes the public 443.
  • Everything that arrives at 443 without the right key is passed by Reality to the local Caddy — and the person sees your site.

Why this is better than either alone. Reality loses its weak spot: it no longer pretends to be someone else’s site — the cover is your own site, on your own domain and with your certificate. The mismatch “going to one IP, calling itself another name” is gone. And people for whom Reality doesn’t get through take the link of the inbound behind the site. One server, one port, two routes.

After that, port 8443 is taken by Caddy and unavailable to other inbounds — the panel refuses with an explanation. If you need 8443 for something, first move Reality off 443.

06·D

Option D — NaiveProxy and SSH

Two backup routes. They are kept not instead of the main ones but alongside — for when the main one stops working for a particular person.

NaiveProxy

Looks like ordinary browser traffic to a website, because technically that’s what it is. In the panel: «Инбаунды» (Inbounds) → create → template «NaiveProxy».

  • It needs a separate name — make up any subdomain (say, files.example.com): not the panel’s and not the one of the inbound behind the site. If you made the asterisk record in step 01, the name already points to the server and DNS needs no changes. If you made individual records, add an A record for it.
  • Port 443, TLS required — the panel gets the certificate by itself.
  • A domain is required by design: Caddy sorts incoming connections by name, and without its own name NaiveProxy has nowhere to be routed.

SSH

The very last line. Slow, but gets through where nothing else does — SSH is rarely blocked, every administrator needs it.

In the panel: «Инбаунды» (Inbounds) → create → engine SSH. Enter the port of your sshd (usually 22). No domain or certificate needed.

An SSH node gives real access to your server, so hand it out selectively and not to the same people as the regular links. The speed is noticeably lower than the other schemes — that’s normal and can’t be fixed with settings.

06·E

Server in Russia — for clients abroad

Usually the server is abroad and the users are in Russia. Then the app sends Russian sites and apps directly and everything else through the server.

Sometimes it’s the other way round: a person lives abroad but needs Russian services — a bank, Gosuslugi, marketplaces. They often don’t let foreign addresses in. For this the server is placed in Russia, and the app works “mirrored”: Russian traffic goes through the server, everything else directly.

How to turn it on

  1. Install the panel on a server in Russia — the same way as in sections 01–06.
  2. In the panel: «Сервер» (Server) → «Настройки» (Settings) → «Панель» (Panel) → «Где стоит сервер» (Where the server is) select «В России» (In Russia) and click «Применить» (Apply).
  3. Give clients links as usual (section 07). The mode is already inside the link: the app turns on the right rules by itself, nothing to configure.
  • The app won’t let users change the mode for such a server — nobody can break things by accident.
  • If you changed the switch after handing out links, clients need to update the subscription (or add the link again) — an old link carries the old mode.
  • The default is «Не в России» (Not in Russia). Ordinary servers need no changes.
  • With third-party panels (3x-ui and others) the link carries no mode. Users choose it themselves in the app: Settings → Where you are (at the very bottom of the settings).
  • The switch affects only connections that go out to the internet directly from this server. The same server can also carry connections for people in Russia — through an exit abroad (section 06·F): their links get the exit’s mode by themselves.

Set the switch correctly. A mistake hits all direct connections of the server: «В России» on a server abroad sends their banks abroad, and the bank may block access. The panel doesn’t check for you where the server actually is.

Check the services you need before promising anything to a client. Some Russian banks and services block not only foreign addresses but hosting addresses too, and a server is exactly a data-centre address. Which ones can’t be said in advance: connect to the new server and open the services the client needs.

06·F

Cascade: entry in Russia, exit abroad

The user connects to a server in Russia, and their traffic goes out to the internet through a server abroad. Why: a Russian address is easier to reach when mobile internet is restricted by “white lists”, and the foreign exit opens blocked sites.

You need two servers with our panel: a Russian one (entry) and a foreign one (exit).

How to set it up

  1. On the foreign server create an ordinary VLESS + Reality connection (section 06·A) and a client for the Russian server — for example, “entry-moscow”. Copy its key (vless://…).
  2. On the Russian server: «Каскад» (Cascade) → «Добавить выход» (Add exit), paste the key. The panel shows what server it is and fills in where it is located. Click «Проверить» (Check) — it should say “работает” (working) and show the exit country.
  3. There, in the «Подключения» (Connections) table, choose the exit for the connection you need. The checkbox «Российские сайты — прямо с этого сервера» (Russian sites — directly from this server) turns on by itself: Russian traffic isn’t sent abroad and back.
  4. Give clients this connection’s links as usual. The app learns by itself that traffic exits abroad — clients with links already issued should update their subscription.
  • Several exits. Add two or three exits and combine them into a group: once a minute the panel checks each one and routes traffic through the fastest live one. If one fails, users won’t notice.
  • One server — different people. For a client abroad keep a connection “directly from this server” («В России» mode, section 06·E); for people in Russia — a separate connection through an exit. Nothing needs switching: each connection has its own label.
  • Cascade is available for Xray connections (VLESS, Trojan). NaiveProxy and SSH always go out directly from the server.

If an exit is turned off or removed from the group, traffic of its connections goes directly from the Russian server — blocked sites stop opening for people. The «Каскад» (Cascade) page highlights such connections. The panel won’t let you delete an exit that someone uses.

06·G

Relay servers — when a carrier cuts connections

Sometimes a mobile carrier in some city cuts connections to foreign servers — for all VPNs at once, regardless of protocol. For this case the app has an «У меня блокировки» (I have blocks) checkbox: the phone connects to an inexpensive server in Russia, which simply passes the stream on to your main server.

  • The relay server decrypts nothing and knows no keys: encryption runs from the phone to the main server. The user keeps the same key and the same internet address.
  • No certificates, domains or panel are needed on the relay server. It is managed only from here, from the main server’s panel.
  • The app goes through a relay only when the user ticks the checkbox. Nothing switches by itself.

What you need

  • A server in Russia: Ubuntu or Debian, root access. It doesn’t need to be powerful — it only forwards traffic.
  • The main server’s panel must have a domain with HTTPS (section 03) — without it the install command doesn’t work, and the panel warns about it.

How to connect one

  1. In the main server’s panel open «Промежуточные серверы» (Relay servers) and click «Добавить» (Add). A name is enough, e.g. “Moscow”. You can leave the address empty — the panel finds it out by itself.
  2. Click «Скопировать команду установки» (Copy install command) and run it on the relay server: 
    on the relay servercurl -fsSL https://panel.example.com/relay-agent/…/install.sh | sudo bash
  3. In a couple of minutes the panel shows «на связи» (online) and the server’s address.
  4. Done. The apps get the address when the subscription updates (automatically every few hours, or with the refresh button in the app). The user just ticks «У меня блокировки».
  • The ports of enabled connections are forwarded. Port 22 is never forwarded — the relay server’s own ssh lives there. So SSH connections on port 22 go directly; the app knows this and warns the user.
  • Turned off or deleted the server in the panel — forwarding on it is removed by itself within a couple of minutes.
  • If the panel is temporarily unreachable, the relay server keeps forwarding with the last settings, including after a reboot.
  • Traffic counter. The table shows how much each relay server has forwarded: ↑ from users, ↓ back, since which date — and a button to reset it. The relay server’s host usually shows about twice as much: every byte passes through the server twice, in and out.
  • To update the agent on a relay server, run the same install command again. If the «Трафик» (Traffic) column says «повторите команду установки» (repeat the install command), the agent is old and doesn’t count traffic (forwarding still works).

The script doesn’t touch the relay server’s firewall. If ufw is on there, the script warns you: allow forwarding yourself (for example, ufw default allow routed). If your host has its own firewall, open the ports of your connections in it.

To check that it works: on the relay server run journalctl -u coc-relay.service -n 20 — it shows which address and ports are forwarded.

07

Users and links

  1. In the panel: «Клиенты» (Clients) → add, choose the inbound you created.
  2. Each client has a link and a QR code — that’s what you give the person.
  3. In the app on a phone or computer the link is added in one action; nothing needs configuring.

A subscription link is a key in itself. An address like https://domain/sub/… gives out all of the user’s nodes without a password. Hand it over personally, don’t post it in group chats and don’t send it to us for support — for troubleshooting, vless://… lines with the ID replaced are enough.

08

Checks

Three checks worth passing before you hand out links.

  1. Services are alive. All four should be active (running): 
    on the serversystemctl status proxy-panel proxy-panel-scheduler xray caddy
  2. The panel responds. It should return {"status":"ok"}: 
    on the servercurl -sf http://127.0.0.1:5000/api/system/health
  3. The site opens. Open https://www.example.com from a phone on mobile internet — your cover site should open, with no certificate warnings.

And only then connect yourself, with your own link, before giving it to others.

09

Updating

The same command as for installation. It detects by itself that the panel is already installed:

on the servercurl -fsSL https://raw.githubusercontent.com/zintar4435-experience/Codex-of-Admin/main/bootstrap.sh | sudo bash

Only the panel code is updated. Users, inbounds and settings stay in place. It can be run as many times as you like.

10

If something goes wrong

Collected from the rakes we stepped on ourselves. Each one cost several hours.

01The panel doesn’t open by domain

Almost always the DNS hasn’t spread yet, or the A record points elsewhere. Check ping panel.example.com: your server’s IP should answer. Until it does, the certificate won’t be issued, and that’s normal.

If the IP is right but there’s no page, look at Caddy: journalctl -u caddy -n 100 --no-pager.

02“Port 8443 is taken”

That’s by design. If you have a Reality inbound on 443, Caddy moves to 127.0.0.1:8443 and shares port 443 with it. That port is then reserved — another inbound can’t take it.

Need 8443 for something else — first move Reality off 443.

03The domain stopped opening for everyone at once

If the server is alive and the services run, most likely the domain itself was blocked, not the server. It happens with free and dynamic zones: they get blocked whole, together with all the other names inside.

Easy to check: the same server answers by IP but not by name. The only cure is moving to your own domain. That’s why the beginning says: the domain must be your own.

04Users disappeared after editing an inbound

This has happened to us. After any edit of an existing inbound, check the client list. If you’re going to change something serious — protocol, transport, port — first make a backup in the panel settings.

And a general rule: creating a new inbound is safer than reworking a working one. The old one can be turned off once everyone has moved to the new one.

05The connection works, but slowly

First rule out the server: try the same link from another internet — mobile, at a friend’s. Slow everywhere — the problem is the server or its channel, and settings won’t fix it.

Slow with one carrier and fast with another — that’s the provider holding back traffic. The sign: fast in the morning, barely alive in the evening. This is exactly where the site disguise helps — the reason it was all done.

06What to look at when it’s unclear

Three logs, one for each part:

journalctl -u proxy-panel -n 100 --no-pager
journalctl -u xray        -n 100 --no-pager
journalctl -u caddy       -n 100 --no-pager

The panel doesn’t open — the first. A client can’t connect — the second. Problems with the domain or certificate — the third.
